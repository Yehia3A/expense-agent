# Decision log

One line per decision, with the reason. IDs D1-D7 come from the project plan in Notion; D8 onward were made during implementation.

| ID | Date | Decision | Reason |
|----|------|----------|--------|
| D1 | 2026-10-20 | `other` is the monthly remainder that gets invested (index fund, gold, crypto). Its budget is your largest line (the amount lives in `data/personal.json`). Investment entries filed as `other` are not flagged; anything else filed as `other` gets `needs_review = 1`. | Your answer to D1. The keyword list lives in `needsReview()` in `src/tools/expenses.ts`. |
| D2 | 2026-10-20 | Import monthly totals only, into `legacy_monthly_totals`, never as fake transactions. Only the months that were actually in the spreadsheet are imported; earlier months stay empty. | Your answer to D2. |
| D3 | 2026-10-19 | Large-amount confirmation threshold = 5,000 EGP (`LARGE_AMOUNT_THRESHOLD` var). | Plan default. |
| D4 | 2026-10-19 | Budget changes copy forward: `set_budget` updates the chosen month and every later month that already has rows, unless `apply_forward=false`. | Plan default. Past months are never touched. |
| D8 | 2026-10-19 | Serve the UI from the Worker itself (Workers Static Assets) instead of a separate Pages project. | One deployment, same origin (no CORS), one Access policy to set up in Phase 3. Cloudflare now recommends this over Pages for new projects. |
| D9 | 2026-10-19 | Spending for a month = real expenses + legacy totals for that month. | A month can be partly in an old spreadsheet and continue in the app. Adding the two keeps that month correct as long as nothing is entered twice. |
| D10 | 2026-10-19 | TOTAL % Used = spending in budgeted categories / sum of budgets. Unbudgeted spending is its own line in the total. | Keeps numerator and denominator over the same categories while never hiding unbudgeted spending. |
| D11 | 2026-10-19 | Large amounts and dates more than 60 days back are not written by the model. The tool returns `needs_confirmation`, and the UI shows a Confirm button that calls `POST /api/expenses` with `confirmed: true`. | Confirmation does not depend on the model reading "yes" correctly. |
| D12 | 2026-10-19 | `/chat` idempotency: the full response is stored in `logs.response` under `request_id`. A retry with the same `request_id` returns the stored response without calling the LLM again. `UNIQUE(request_id, line_index)` stays as a database-level backstop. | A re-run of the LLM could return different items, so line-level dedupe alone is not enough. |
| D13 | 2026-10-19 | Provisional default model: `openai/gpt-oss-120b` on Groq (OpenAI-compatible API). OpenRouter works through the same client. | Free tier, supports tool calling. Phase 5 evals pick the real default. |
| D14 | 2026-10-19 | Until Phase 3, an optional `APP_TOKEN` secret protects `/api` and `/chat` (Bearer header). | Plan's fallback auth. Cloudflare Access is added in Phase 3, before real data goes into the deployed app. |
| D15 | 2026-10-19 | `add_expense` takes an `items` array, so a multi-item message is one call and one atomic batch. | Fewer round trips, one `request_id`, and `line_index` comes from array order. |
| D16 | 2026-10-19 | Tool inputs are validated with zod; the JSON Schemas sent to the LLM are generated from the same zod schemas. | One definition of each tool for `/chat`, `/api` and (Phase 6) `/mcp`. |
| D17 | 2026-10-19 | The model passes a `date_token` (`today`, `yesterday`, `days_ago:N`, `weekday:fri`, `day:5`, `date:YYYY-MM-DD`); code resolves it in Africa/Cairo time. | Plan F2: the model never produces the stored date. |
| D18 | 2026-10-19 | Non-EGP expenses are stored as entered but left out of budget totals and summaries; the budget view lists them separately. | Plan scope: no currency conversion. Adding USD to EGP totals would be wrong. |
| D19 | 2026-10-19 | Tests use `@cloudflare/vitest-plugin` 1.3.6 (the renamed `vitest-pool-workers`), with `compatibility_date` 2026-09-15 so the bundled test runtime supports it. | Plan: Vitest + Miniflare, pinned versions at least two weeks old. |
| D20 | 2026-10-19 | The UI is plain JavaScript (no build step), not TypeScript. | Three small files; a bundler would add setup without adding safety for this size. Worker code stays TypeScript. |
| D21 | 2026-10-19 | `scripts/mock-llm.mjs` is a keyword-based fake of the OpenAI API for local UI work without a key. It is not a parser and is never deployed. | Lets the full stack run locally; real behavior is measured with real models in Phase 5. |
| D22 | 2026-10-20 | The Worker verifies the Cloudflare Access JWT itself (signature against the team's certs, issuer, audience, expiry), and fails closed: with no Access and no `APP_TOKEN` configured it serves only localhost. | Access at the edge alone leaves the raw workers.dev URL open; a forgotten secret should mean "down", not "public". |
| D23 | 2026-10-20 | Rate limits are global fixed windows counted in D1 (`rate_limits` table), not the Workers rate-limit binding. | Works identically in `wrangler dev` and tests, is exact, and costs one D1 write per request, well inside the free tier for one user. |
| D24 | 2026-10-20 | Chart.js 4.5.1 is vendored into `public/vendor/` instead of loaded from a CDN. | The CSP allows only same-origin scripts, and Access-protected pages should not depend on third-party hosts. `npm run vendor:chart` refreshes it. |
| D25 | 2026-10-20 | History lists months newest first; its per-month budget table is read-only. | The current month is what you look at most. Editing a past month's budget from History would copy forward into later months by surprise; budgets are edited on Track. |
| D26 | 2026-10-20 | The fast path is deliberately strict: anything that looks like a question, command, other date, other currency or a number with a thousands separator goes to the LLM, and every item must already be in the merchant cache. | A missed fast path costs one LLM call; a wrong one writes a wrong expense. The eval shows 0 false writes for the fast path alone. |
| D27 | 2026-10-20 | The merchant cache learns from every saved row except those flagged for review, and a manual category change overwrites what it learned. | Corrections are the best labels; a flagged 'other' is a guess and must not spread. |
| D28 | 2026-10-20 | `LLM_FALLBACK_MODEL` (default `llama-3.1-8b-instant`) takes over for the rest of a request when the main model answers 429. | Groq's free daily token cap for the large model fits only a few dozen LLM messages a day (plan R2). |
| D29 | 2026-10-20 | The MCP server is hand-written (stateless Streamable HTTP, JSON responses), not built on the SDK; the SDK is used only by the test client. | Keeps the Worker small for the free plan's 10 ms CPU budget and makes the protocol visible, which is part of the project's learning goal. |
| D30 | 2026-10-20 | Over MCP, `add_expense` accepts `confirmed: true` for large or old expenses. | MCP clients show every tool call to the user before it runs, so the confirmation is the user's; in `/chat` the model still never gets this flag (D11). |
| D31 | 2026-10-20 | Your real budgets and spreadsheet totals live in gitignored `data/personal.json`, seeded by `npm run db:seed-personal:*`; migration 0003 (which held them) was removed before any remote deploy, and tests use fixtures. | The plan's Phase 7 asks for no personal data in the repo. The published history starts after this, so it contains no personal numbers. |
| D32 | 2026-10-20 | The browser signs in with a username and password (PBKDF2-SHA256, 20,000 iterations) and gets a 30-day sliding session in an HttpOnly, Secure, SameSite=Strict cookie; D1 stores only the session token's SHA-256. The first account needs the APP_TOKEN as a one-time setup key; APP_TOKEN stays valid as a Bearer token for scripts and MCP. Sign-in is rate-limited to 10 tries per 15 minutes per IP and 60 per hour overall. | You asked for a normal login that the browser can autofill and that lasts 30 days. The iteration count is low because the free plan allows 10 ms of CPU per request; the rate limits stop online guessing instead. |
| D33 | 2026-10-20 | Dark theme by default, with a switch in both headers that is remembered per browser; in-page dialogs and toasts replace the browser's confirm() and prompt() boxes. | Your request. theme.js sets the theme before the first paint so there is no flash. |
| D34 | 2026-10-20 | The app is public and multi-user: anyone can sign up with a username and password, and every row of personal data (expenses, budgets, legacy totals, learned merchant words, logs) carries a `user_id` that every query filters on. Unique keys include the user (e.g. `(user_id, request_id, line_index)`), so reusing someone else's ids can't reach their rows. | You want the app free for anyone. Tests in `test/isolation.test.ts` pin the isolation down. |
| D35 | 2026-10-20 | Data from before accounts existed is marked `unclaimed` (invisible to everyone) by migration 0007, and moved into an account only by the owner's `npm run claim:remote -- <username>`, which also seeds `data/personal.json`. | Nobody who signs up first can inherit your data. |
| D36 | 2026-10-20 | Each account gets a personal API token for MCP and scripts (one at a time, stored as SHA-256, created only from a browser session); the single shared `APP_TOKEN` is gone. | A shared key can't say whose data a request is for. |
| D37 | 2026-10-20 | Limits: per account 20 chat messages a minute and 200 a day; all accounts together 800 LLM messages a day (`LLM_RATE_PER_DAY`), checked only when a message actually goes to the model; sign-ups 5 per IP and 300 overall per day; `SIGNUP_OPEN` can close sign-ups. | One free Groq key and one free D1 quota serve everyone, and nothing must be billable. |
| D38 | 2026-10-20 | Accounts can be deleted by their owner (password required), removing every row of their data. Forgotten passwords are reset by the operator with `npm run reset-password:remote -- <username>` (temporary password, sessions revoked). | Privacy for other people's data; there's no email for self-service resets. |
| D39 | 2026-10-20 | Cloudflare Access becomes an optional extra gate in front of sign-in (for a private deployment), no longer an identity on its own. | With many users, identity has to come from the account, not from the edge. |
| D40 | 2026-10-21 | Voice input records in the browser (MediaRecorder), stops itself after 1.4 s of silence (30 s max), and is transcribed by Groq Whisper (`whisper-large-v3-turbo`, free: 2,000 clips and 8 audio hours a day) through `POST /api/transcribe`. Limits: 10 clips a minute and 100 a day per account, 1,500 a day overall. Driving mode is a full-screen view with one huge button, a 3-second cancellable countdown before sending, and the screen kept on (Wake Lock). | Free, and unlike the browser's built-in speech recognition it works in Brave, Firefox and on iPhone, and handles English, Arabic and mixed speech. |
| D41 | 2026-10-21 | Categories belong to each account: up to 10, picked from 15 suggestions or written freely (any language), each with a monthly budget, plus an automatic Other. Expenses store a stable key, so renaming keeps history; removing a used category hides it but keeps its spending in reports. The fixed global list and its foreign keys are gone (migration 0008); the model and MCP clients get the account's own list. | Your request: people track what matters to them. The shared merchant vocabulary only applies to categories an account actually has. |
| D42 | 2026-10-21 | History starts with the account: the sign-up month and the month before it, reaching further back only for months that have records (imported totals or back-dated expenses), up to 24 months. | Your request: no rows of empty months from before you joined. |
| D43 | 2026-10-21 | Smarter categorizing: the model gets, for each of the account's categories, up to 6 items the user filed there in the last 120 days, plus rules to prefer the most specific category (a "Healthy snacks" category beats a general food one for a protein bar). The fast path ignores the shared starter words for any item that shares a word with one of the user's own (non-suggested) category names; words the user taught it still apply. | Your request: custom categories like "Healthy snacks" should catch protein bars, greek yogurt and healthy drinks. |
| D44 | 2026-10-21 | Quick log: up to 5 one-tap buttons above the chat box for the items you log most (same note and category at least twice in the last 90 days, EGP only, active categories only), each using the amount you entered last time. A tap saves through `POST /api/expenses` without the model, with Undo, and large amounts still ask for confirmation. | Your request: faster logging when you're busy, and it costs no AI quota. |
| D45 | 2026-10-21 | Each account has a currency (`users.currency`, migration 0009; existing accounts stay EGP). Setup pre-picks it from the device's time zone; the list has 30 main currencies plus "Other currency…" for any ISO code, and it can be changed from the account menu or the category editor. Budgets, totals, history, reports and quick log use it; expenses in another currency are kept but left out of totals (as in D18). Changing it relabels records in the old currency, without converting. Large-amount confirmation uses a per-currency limit of about 500 US dollars (EGP keeps `LARGE_AMOUNT_THRESHOLD`); codes outside that table skip it. | Your request: people outside Egypt can use the app. No exchange rates means no conversion; relabelling keeps budgets (which carry no currency) and spending together. |
| D46 | 2026-10-21 | Each account has a city and time zone (`users.timezone`, `users.city`, migration 0010; existing accounts stay on Cairo). The time zone comes with the sign-in lookup at no extra query, and sets "today", the current month and history for the web app, chat and MCP. The picker searches about 7,300 cities (`public/data/cities.json`, 90 KB gzipped, built from the `city-timezones` package and loaded only when the picker opens), showing each match's local time; setup pre-picks the biggest city in the device's time zone. Past expenses keep their dates. | Your request: people anywhere get the right date. A city list is easier than choosing from 400 raw time-zone names. |
| D47 | 2026-10-27 | Expenses can carry optional notes (`expenses.details`, migration 0011). The AI adds them only for out-of-the-ordinary one-offs the user explains ("2000 for fixing car wheel bearing" → item "car wheel bearing", notes "Fixing the car's wheel bearing"), never for everyday spending; code files any item with notes under Other and doesn't flag it for review. Notes can also be added, changed or removed with Edit, without changing the category. They appear only on the Report page (a Notes card, any currency) and in `monthly_report`. One-offs with notes don't teach the merchant cache, and the fast path takes items of 3+ words only on an exact match, so a description isn't filed by one known word ("car"). | Your request: a place for the story behind unusual spending, without cluttering the everyday views. |
